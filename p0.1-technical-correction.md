## P0.1-1 — RESERVATION IDEMPOTENCY

### CURRENT DESIGN

```
reserve_contact_budget(customer_id, merchant_id, case_id, decision_epoch, policy_version, candidates)
  BEGIN (serializable)
    SELECT ... FOR UPDATE
    if reserved_count >= cap: reject                                  <- wrong quantity
    UPDATE budget SET reserved_count += 1 WHERE version = expected    <- counter moves first
    INSERT contact_reservation ...                                    <- key may already exist
      on IntegrityError: return existing reservation                  <- increment NOT undone
  COMMIT
```

### PROBLEM

Six defects, four of them critical:

1. **The cap check reads the wrong quantity (I-1).** `reserved_count` is decremented on execution, so it measures *in-flight* contacts, not *used* contacts. `reserved_count >= cap` is therefore never true in steady state. The 4/month cap — D1's entire enforcement mechanism — does nothing.
2. **Increment precedes insert (I-2).** The idempotent-retry path returns *after* the counter has moved, and the enclosing transaction commits. Every retry of the same logical decision costs a slot.
3. **The key contains a timestamp (I-3)**, so a retry never presents the same key and never reaches the dedup path at all.
4. **`release` / `mark_executed` / `expire` are unguarded (I-4, I-5)**, so a repeat call — or a cleanup job racing the executor — moves counters again.
5. **Missing-row path is not race-safe (I-6).**
6. **The SQL does not run on the prototype stack (I-7).**

### REQUIRED CHANGE

- Enforce the invariant **`reserved_count + consumed_count <= cap`**, and check *that sum* inside the `WHERE` clause of a single conditional `UPDATE`.
- Push the invariant into the database as a `CHECK` constraint, so any residual bug raises instead of over-contacting.
- Make `idempotency_key` **caller-supplied and deterministic**; `decision_epoch` becomes an **arbitration-run identifier**, never a clock reading.
- **Look up by idempotency key first and return before touching any counter.**
- Make every lifecycle transition a **compare-and-swap on `status`**, and derive counter movement from the CAS rowcount — never call it unconditionally.
- Fix the missing-row path with `INSERT … ON CONFLICT DO NOTHING`, then re-read.
- Commit to **one dialect for the prototype: SQLite, WAL, `BEGIN IMMEDIATE`.** Under `BEGIN IMMEDIATE` the transaction is fully serialised, which makes the `version` column belt-and-braces; keep it so the identical code is correct on Postgres, where the conditional `UPDATE` is the single point of truth.

**Key derivation — deterministic, stable under retry:**

```python
def contact_idempotency_key(merchant_id, customer_id, case_id, action_type, decision_epoch):
    # decision_epoch is the arbitration RUN id (e.g. "run:batch-7:seed-42"), assigned
    # once per arbitration tick and reused verbatim by every retry of that tick.
    return hashlib.sha256(
        "|".join([merchant_id, customer_id, case_id, action_type, decision_epoch]).encode()
    ).hexdigest()
```

**Transaction ordering — read by key first, counter last:**

```python
def reserve_contact_budget(merchant_id, customer_id, action_type, idempotency_key, *,
                           case_id, decision_epoch, policy_version,
                           flags_version, month, clock) -> ReservationResult:
    """
    INVARIANT: one idempotency_key => at most one reservation => at most one budget slot.
    """
    with db.transaction("BEGIN IMMEDIATE"):

        # --- Step 1: idempotent short-circuit, BEFORE any counter is touched --------
        existing = db.one("""
            SELECT id, status FROM contact_reservation
             WHERE merchant_id = ? AND idempotency_key = ?
        """, (merchant_id, idempotency_key))
        if existing:
            return ReservationResult(status="reserved", reservation_id=existing["id"],
                                     replayed=True, terminal_status=existing["status"])

        # --- Step 2: ensure the budget row exists (race-safe) -----------------------
        db.execute("""
            INSERT INTO customer_month_budget
                   (merchant_id, customer_id, month, cap,
                    reserved_count, consumed_count, version, updated_at)
            VALUES (?, ?, ?, ?, 0, 0, 1, ?)
            ON CONFLICT (merchant_id, customer_id, month) DO NOTHING
        """, (merchant_id, customer_id, month,
              policy.cap_for(merchant_id), clock.now_iso()))

        # --- Step 3: single atomic conditional increment ----------------------------
        #     cap is checked against reserved + consumed, inside the WHERE clause
        n = db.execute("""
            UPDATE customer_month_budget
               SET reserved_count = reserved_count + 1,
                   version        = version + 1,
                   updated_at     = ?
             WHERE merchant_id = ? AND customer_id = ? AND month = ?
               AND reserved_count + consumed_count < cap
        """, (clock.now_iso(), merchant_id, customer_id, month)).rowcount

        if n == 0:
            record_suppression(merchant_id, customer_id, case_id,
                               decision_epoch, reason="budget_exhausted")
            return ReservationResult(status="rejected", reason="budget_exhausted")

        # --- Step 4: create the reservation ------------------------------------------
        rid = deterministic_id(idempotency_key)      # replay-stable id
        inserted = db.execute("""
            INSERT INTO contact_reservation
                   (id, merchant_id, customer_id, month, case_id, action_type,
                    decision_epoch, idempotency_key, status, reserved_at, expires_at,
                    policy_version, flags_version_at_decision)
            VALUES (?,?,?,?,?,?,?,?, 'reserved', ?, ?, ?, ?)
            ON CONFLICT (merchant_id, idempotency_key) DO NOTHING
        """, (rid, merchant_id, customer_id, month, case_id, action_type,
              decision_epoch, idempotency_key, clock.now_iso(),
              clock.plus_minutes_iso(30), policy_version, flags_version)).rowcount

        if inserted == 0:
            # cross-process race on the same key: roll back our increment entirely,
            # then return the winner's reservation on a fresh read
            raise RollbackAndReturnExisting(merchant_id, idempotency_key)

    return ReservationResult(status="reserved", reservation_id=rid, replayed=False)
```

**Guarded lifecycle transitions** — the CAS rowcount is the only thing permitted to move a counter:

```python
def mark_reservation_executed(merchant_id, reservation_id, clock) -> bool:
    """Idempotent. A second call is a no-op that returns True."""
    with db.transaction("BEGIN IMMEDIATE"):
        moved = db.execute("""
            UPDATE contact_reservation
               SET status = 'executed', executed_at = ?
             WHERE id = ? AND merchant_id = ? AND status = 'reserved'      -- CAS
        """, (clock.now_iso(), reservation_id, merchant_id)).rowcount
        if moved == 0:
            return already_in(merchant_id, reservation_id, ('executed',))  # no counter change
        db.execute("""
            UPDATE customer_month_budget
               SET reserved_count = reserved_count - 1,
                   consumed_count = consumed_count + 1,
                   version        = version + 1
             WHERE (merchant_id, customer_id, month) =
                   (SELECT merchant_id, customer_id, month
                      FROM contact_reservation WHERE id = ?)
        """, (reservation_id,))
    return True


def release_reservation(merchant_id, reservation_id, reason, clock) -> bool:
    """Idempotent. Only a 'reserved' row may be released — never an executed one."""
    with db.transaction("BEGIN IMMEDIATE"):
        moved = db.execute("""
            UPDATE contact_reservation
               SET status = 'released', released_at = ?, release_reason = ?
             WHERE id = ? AND merchant_id = ? AND status = 'reserved'      -- CAS
        """, (clock.now_iso(), reason, reservation_id, merchant_id)).rowcount
        if moved == 0:
            return already_in(merchant_id, reservation_id, ('released', 'expired'))
        db.execute("""
            UPDATE customer_month_budget
               SET reserved_count = reserved_count - 1, version = version + 1
             WHERE (merchant_id, customer_id, month) =
                   (SELECT merchant_id, customer_id, month
                      FROM contact_reservation WHERE id = ?)
        """, (reservation_id,))
    return True


def expire_reservations(merchant_id, clock) -> int:
    """Same CAS pattern, so expiry can never race the executor (fixes I-5)."""
    n = 0
    with db.transaction("BEGIN IMMEDIATE"):
        for r in db.all("""SELECT id FROM contact_reservation
                            WHERE merchant_id = ? AND status = 'reserved'
                              AND expires_at < ?""", (merchant_id, clock.now_iso())):
            if db.execute("""UPDATE contact_reservation SET status = 'expired'
                              WHERE id = ? AND status = 'reserved'""", (r["id"],)).rowcount:
                db.execute("""UPDATE customer_month_budget
                                 SET reserved_count = reserved_count - 1,
                                     version = version + 1
                               WHERE (merchant_id, customer_id, month) =
                                     (SELECT merchant_id, customer_id, month
                                        FROM contact_reservation WHERE id = ?)""", (r["id"],))
                n += 1
    return n
```

**`execution_unknown`** (used by P0.1-8): when the send provider returns an ambiguous result, the reservation moves `reserved → execution_unknown` and **the slot stays held**. It is never auto-released — releasing on an ambiguous send is exactly how a double contact happens. Resolution comes from the provider delivery webhook or the reconciliation job, both using the same CAS pattern.

## P0.1-2 — COUNTERFACTUAL RECOVERY ATTRIBUTION

### CURRENT DESIGN

One `RecoveryOutcome` row per opportunity, carrying `baseline_recovered` *and* `treatment_recovered`; all three systems consume the same `ExperimentOpportunitySet`; incremental recovery is `treatment_total − baseline_total`.

### PROBLEM

- **A counterfactual is stored as an observation (I-9).** For any real opportunity only one arm's outcome exists. Writing both onto one row makes an unfalsifiable claim look like data.
- **Randomisation unit is wrong for this system (I-10).** D1's entire mechanism is *cross-opportunity arbitration for one customer*. If a customer's cart opportunity is in control and their invoice opportunity is in treatment, treatment's suppression decision changes what control does — the arms are not independent, and the estimator has no clean interpretation.
- **Totals are subtracted (I-11).** Different arm sizes or composition make the difference meaningless.

### REQUIRED CHANGE

Split the harness into **two explicitly labelled modes**, and never mix their vocabulary.

**MODE A — SIMULATION (paired, within-subject).** Valid *only* because the world is authored: the payer-response function is a known, deterministic function, so the counterfactual is *computed*, not observed. Every number produced here is labelled **SIMULATED COUNTERFACTUAL**.
- All arms consume the identical `ExperimentOpportunitySet` (hash-asserted).
- The response function must be **arm-blind** and driven by **common random numbers**: the RNG stream is keyed by `opportunity_id`, not by call order, so the same opportunity given the same action draws the same outcome in every arm. Without this, an arm can simply get luckier, and the variance swamps the effect.
- Analysis is **paired by seed**: Wilcoxon signed-rank (revenue is skewed) plus a paired mean difference with a 95% CI.

**MODE B — RANDOMISED EXPERIMENT (between-subject).** The only design valid against real traffic.
- **Randomisation unit = `(merchant_id, canonical_customer_id)`**, never an opportunity. Every opportunity inherits its customer's arm.
- Assignment is **deterministic and reproducible**, not RNG-stateful: `arm_index = int(sha256(experiment_id | merchant_id | canonical_customer_id), 16) % n_arms`. A customer reappearing later lands in the same arm.
- **Blocked/stratified** on merchant, opportunity-count bucket, and total-amount-at-risk decile, to control the skew.
- **Unit of analysis = the randomisation unit.** Aggregate to per-customer values first, then compare across customers. Analysing at opportunity level while randomising at customer level understates the standard error.

**Correct aggregation**

```python
def incremental_effect(outcomes, experiment) -> Effect:
    """
    Randomisation is at the customer level, so the customer is the unit of analysis.
    Never subtract arm totals.
    """
    per_customer = (outcomes
        .groupby(["arm", "merchant_id", "canonical_customer_id"])
        .agg(recovered=("recovered_paise", "sum"),
             contacts=("contacts_sent", "sum"),
             at_risk=("validated_recoverable_paise", "sum"))
        .reset_index())

    t = per_customer[per_customer.arm == experiment.treatment_arm]
    c = per_customer[per_customer.arm == experiment.control_arm]

    # difference in MEANS per customer, not difference in totals
    delta_mean = t.recovered.mean() - c.recovered.mean()
    se = sqrt(t.recovered.var(ddof=1)/len(t) + c.recovered.var(ddof=1)/len(c))  # Welch
    ci = (delta_mean - 1.96*se, delta_mean + 1.96*se)

    # recovery RATE: difference in proportions, same unit
    rate_delta = t.recovered.gt(0).mean() - c.recovered.gt(0).mean()

    return Effect(
        delta_recovered_per_customer=delta_mean,
        ci95=ci,
        recovery_rate_delta=rate_delta,
        # extrapolation, labelled as such — never presented as an observed total
        projected_total_if_all_treated=delta_mean * per_customer.canonical_customer_id.nunique(),
        inconclusive=(ci[0] <= 0 <= ci[1]),
    )
```

## P0.1-3 — SELF-CURE VS INCREMENTAL RECOVERY

### CURRENT DESIGN

`RecoveryOutcome.status` enumerates `OPEN, SELF_CURED, CLOSED_UNRECOVERABLE, INTERVENED, RECOVERED`, with no timing rules attached — nothing states *when* a payment counts as caused by an intervention.

### PROBLEM

Without an explicit timeline, a payment that arrived *before* any contact was sent is indistinguishable from one that arrived because of it. That is the single easiest way to inflate the headline number, and the first thing a hostile reviewer tests.

### REQUIRED CHANGE

Three explicit parameters, fixed per experiment and identical across arms:

```
observation_window_days   = 30   # from opportunity_created_at
attribution_window_hours  = 72   # after an intervention is DELIVERED
self_cure_grace_hours     = 24   # informational; see rule 1
```

Attribution rules, evaluated in order:

| # | Condition | Status | Counts toward the intervention effect? |
|---|---|---|---|
| 1 | `payment_at < first_intervention_delivered_at` | `SELF_CURED` | **No — always, regardless of any window** |
| 2 | no intervention ever delivered, payment within observation window | `SELF_CURED` | No |
| 3 | `delivered_at <= payment_at <= delivered_at + attribution_window` | `RECOVERED_ATTRIBUTED` | Yes, attributed to that decision |
| 4 | payment after the last delivery + attribution window, still inside observation window | `RECOVERED_UNATTRIBUTED` | Reported separately; never called intervention-caused |
| 5 | multiple deliveries precede the payment | `RECOVERED_ATTRIBUTED` to the **last** delivery (last-touch); the full contact sequence is stored | Yes |
| 6 | `0 < recovered < validated_recoverable − tds_tolerance` | `PARTIAL_RECOVERY` | Yes, at the recovered amount; `residual_paise` carried |
| 7 | payment after the observation window closes | `NOT_RECOVERED` for the primary metric; logged as `post_window_payment` | No — right-censored, reported as a diagnostic |
| 8 | Stage 0 closed it as never-at-risk | `CLOSED_NOT_AT_RISK` | Excluded from the recovery denominator entirely |

Two consequences worth stating on camera:

- **Per-action attribution is a diagnostic, not the claim.** In randomised mode the headline is the *arm-level difference*, which is valid regardless of which specific contact "caused" a payment. Last-touch is reported alongside a first-touch sensitivity so the choice is visible.
- **Self-cure is measured in every arm, and the arms must agree.** A material difference in self-cure rate between arms means assignment or the simulator is broken — it is a validity check, not a result.

### UPDATED DESIGN

```python
# NEW
class OutcomeStatus(str, Enum):
    OPEN                    = "open"
    CLOSED_NOT_AT_RISK      = "closed_not_at_risk"      # Stage 0
    SELF_CURED              = "self_cured"
    RECOVERED_ATTRIBUTED    = "recovered_attributed"
    RECOVERED_UNATTRIBUTED  = "recovered_unattributed"
    PARTIAL_RECOVERY        = "partial_recovery"
    NOT_RECOVERED           = "not_recovered"

def classify_outcome(opp, interventions, payments, cfg) -> ClassifiedOutcome:
    if opp.stage0_closed:
        return ClassifiedOutcome(OutcomeStatus.CLOSED_NOT_AT_RISK, 0, None)

    window_end = opp.created_at + days(cfg.observation_window_days)
    pays = [p for p in payments if opp.created_at <= p.at <= window_end]
    late = [p for p in payments if p.at > window_end]
    delivered = sorted(i.delivered_at for i in interventions if i.delivered_at)

    if not pays:
        return ClassifiedOutcome(OutcomeStatus.NOT_RECOVERED, 0, None,
                                 post_window_payment=bool(late))

    total = sum(p.amount_paise for p in pays)
    first_pay = min(p.at for p in pays)

    if not delivered or first_pay < delivered[0]:
        return ClassifiedOutcome(OutcomeStatus.SELF_CURED, total, None)   # rules 1 and 2

    preceding = [d for d in delivered if d <= first_pay]
    last_touch = max(preceding)
    if first_pay <= last_touch + hours(cfg.attribution_window_hours):
        status = OutcomeStatus.RECOVERED_ATTRIBUTED
        decision = decision_for(last_touch)
    else:
        status = OutcomeStatus.RECOVERED_UNATTRIBUTED                     # rule 4
        decision = None

    if total < opp.validated_recoverable_paise - cfg.tds_tolerance_paise:
        status = OutcomeStatus.PARTIAL_RECOVERY                           # rule 6

    return ClassifiedOutcome(status, total, decision,
                             residual_paise=opp.validated_recoverable_paise - total,
                             first_touch_decision=decision_for(min(preceding)))
```

## P0.1-4 — REPRODUCIBILITY

### CURRENT DESIGN

`generate_experiment_opportunity_set(seed, num_opportunities, customer_count)`, with timestamps produced from wall-clock time and money held as `float`.

### PROBLEM

`datetime.now()` makes the dataset a function of *when* it was generated, so the P0-3 content hash changes run to run and proves nothing. Float money makes sums order- and platform-dependent, so even a fixed dataset can hash differently.

### REQUIRED CHANGE

- `reference_timestamp` becomes an explicit input. **Every** timestamp in the generator, simulator and decision path is derived from an injected `Clock`; `datetime.now()` is banned from the package and the ban is enforced by a test.
- **All money is integer paise.** No floats anywhere in the data model or the metrics.
- RNG is never global: one `random.Random` per entity, seeded as `Random(sha256(seed | entity_id))`, so generation is order-independent and gives common random numbers for free (P0.1-2).
- The hash covers the **config**, not just the data: `dataset_hash = sha256(canonical_json(config) + canonical_json(opportunities))`, keys sorted, integers only.

### UPDATED DESIGN

```python
# NEW
@dataclass(frozen=True)
class GeneratorConfig:
    seed: int
    reference_timestamp: str      # fixed ISO-8601, e.g. "2026-01-01T00:00:00Z"
    num_opportunities: int
    customer_count: int
    customer_overlap_rate: float  # fraction of customers appearing in >=2 streams
    stream_mix: tuple[tuple[str, float], ...]
    amount_distribution: str
    downtime_events: int
    def config_hash(self) -> str:
        return sha256(canonical_json(asdict(self)))

class Clock(Protocol):
    def now_iso(self) -> str: ...
class FixedClock:                 # the only clock used by generator, sim and eval
    def __init__(self, ref): self.t = parse(ref)
    def now_iso(self): return iso(self.t)
    def advance(self, **kw): self.t += timedelta(**kw)

def generate_opportunity_set(cfg: GeneratorConfig) -> ExperimentOpportunitySet:
    clock = FixedClock(cfg.reference_timestamp)
    def rng_for(entity_id): return random.Random(int(sha256(f"{cfg.seed}|{entity_id}"), 16))
    ...   # all amounts int paise; all times = reference_timestamp + deterministic offsets
```

## P0.1-5 — BASELINE FAIRNESS

### CURRENT DESIGN

All three arms consume the same `ExperimentOpportunitySet` with an asserted input hash. Treatment additionally consumes the downtime webhook.

### PROBLEM

Input equality is necessary but not sufficient. Two gaps remain:

1. **The downtime signal is a confound (I-16).** If treatment beats baseline, no part of that lift can be assigned to unification versus downtime consumption. Any claim about D1 or D2 individually is unsupported.
2. **The baseline is authored by the same team that authors the winner.** Nothing currently prevents tuning treatment on the evaluation seeds while the baseline stays at its first-draft parameters.

### REQUIRED CHANGE

**Declare the split explicitly and put it in the README.**

| Shared experimental state — identical, hash-asserted | System-specific intelligence — the thing under test |
|---|---|
| events, opportunity set, ground truth | baseline: published-style per-agent retry/recovery rules |
| customer identities and initial state | treatment: Stage 0 validation gate |
| transaction amounts, timestamps | treatment: cross-stream shared contact ledger + arbitration |
| merchant policies, caps, quiet hours, opt-outs | treatment: recovery scoring / ranking |
| payment state, gateway state | treatment (A3 only): downtime-signal consumption |
| payer-response world model + RNG streams | |

**Run four arms, and read the differences as separate claims** (Option B in the brief — preferred, because it isolates D2):

```
A0  rules engine                              (Baseline A)
A1  four independent agents, no shared ledger  (Baseline B)
A2  unified engine, downtime signal DISABLED
A3  unified engine, downtime signal ENABLED

A1 - A0  = value of per-stream agents over static rules
A2 - A1  = value of unification: shared ledger + arbitration + Stage 0   <- D1 and D3
A3 - A2  = value of downtime-signal consumption                          <- D2, isolated
```

Add `A2_no_stage0` as a fifth simulation-only arm if Stage 0 needs isolating from the ledger. Simulation mode can afford five arms (paired, cheap); randomised mode should run two, with the primary comparison pre-registered.

**Anti-strawman rules for the baselines:**
- Baseline logic and parameters are **frozen before any treatment result is seen**, and the freeze is recorded as a git tag in the README.
- Baselines are tuned on a **separate tuning seed set**, disjoint from the evaluation seeds, using the same effort budget as treatment.
- `arm.signals_enabled` is an explicit field, printed in the results table, so any asymmetry is visible rather than buried.

## P0.1-8 — POLICY / RESERVATION ORDERING

### CURRENT DESIGN

Arbitration reserves the budget, then runs `policy_engine.check(...)` on the winner and recurses on failure — so a slot can be reserved for an action that policy later rejects, and there is no re-check between decision and send.

### PROBLEM

- A hard-blocked action can consume a slot before it is rejected (and, given I-4, the release path may not return it correctly).
- **TOCTOU (I-17)**: a customer can opt out, or a dispute can open, between arbitration and execution. The decision was valid when made and harmful when executed.

### REQUIRED CHANGE

Reorder, and add an execution-time guard:

```
Recovery Opportunity
      |
Stage 0 Validate
      |
Stage 1 Diagnose
      |
Stage 2 Generate + Score candidates      (pure function, no I/O, no side effects)
      |
HARD POLICY FILTER                       (opt-out, dispute, quiet hours, live promise,
      |                                   retry cap; drops candidates entirely)
Payment-State Coordination               (P0.1-6/7: unknown retry state => drop retry candidates)
      |
ARBITRATION                              (rank survivors; ABSTAIN is always a candidate)
      |
ATOMIC BUDGET RESERVATION                (only ever for a policy-cleared winner)
      |
EXECUTION  -- re-check flags_version inside the same transaction as reserved->executed
      |
OUTCOME
```

**The TOCTOU guard.** `customer_flags` gains a monotonic `flags_version`, bumped on every change to opt-out, dispute or promise state. Arbitration stamps `flags_version_at_decision` on the reservation. Execution re-reads the current version inside the same transaction that flips `reserved → executed`:

```python
def execute_reservation(merchant_id, reservation_id, clock) -> ExecutionResult:
    with db.transaction("BEGIN IMMEDIATE"):
        r = load_reservation(merchant_id, reservation_id)
        if r.status != "reserved":
            return ExecutionResult.replayed(r.status)

        current = db.one("""SELECT flags_version FROM customer_flags
                             WHERE merchant_id=? AND customer_id=?""",
                         (merchant_id, r.customer_id))["flags_version"]
        if current != r.flags_version_at_decision:
            recheck = policy.hard_check(merchant_id, r.customer_id, r.action_type)
            if not recheck.allowed:
                release_reservation(merchant_id, reservation_id,
                                    reason=f"stale_decision:{recheck.reason}", clock=clock)
                audit("stale_decision_aborted", reservation_id, recheck.reason)
                return ExecutionResult.aborted(recheck.reason)
            r = restamp(r, current)          # still permitted; adopt the new version

        mark_reservation_executed(merchant_id, reservation_id, clock)   # CAS

    # the send happens AFTER commit; an ambiguous result never auto-releases
    try:
        provider_ref = sender.send(r)
        record_send(reservation_id, provider_ref)
        return ExecutionResult.sent(provider_ref)
    except AmbiguousProviderResponse:
        set_status(reservation_id, "execution_unknown")   # slot stays held
        enqueue_reconciliation(reservation_id)
        return ExecutionResult.unknown()
```

## P0.1-9 — TENANT-SAFE CUSTOMER STATE

### CURRENT DESIGN

P0-2 added `merchant_id` to the tables. Derived state — `CustomerRecoveryState`, caches, features, training data, analytics, audit exports — is not covered.

### PROBLEM

The tables can be perfectly scoped while a cache keyed on `email` merges two merchants' customers, or a model feature `customer_prior_failures` is computed with a global join. The leak reappears one layer up.

### REQUIRED CHANGE

- **Identity is merchant-local by definition.** `canonical_customer_id` is unique only within a merchant; no global customer identity exists anywhere in the system. Resolution runs inside a merchant partition and never sees another merchant's records.
- Every access goes through a `TenantScope` that the data-access layer requires; queries without a `merchant_id` predicate are rejected at runtime, not by review.
- **Cache keys are prefixed** `{merchant_id}:{namespace}:{key}` with no exceptions.

- Training data, evaluation exports, traces and audit dumps are merchant-partitioned.

### UPDATED DESIGN

## P0.1-10 — DECISION AUDITABILITY

### CURRENT DESIGN

`arbitration_decision` stores `candidates_considered` and `suppressed_cases` as JSON, with a hardcoded suppression reason (I-8). No model output, features or probabilities are recorded.

### PROBLEM

The system cannot answer "why did the engine select this action?" from data. Any explanation would be generated after the fact by an LLM reading the outcome — which is narration, not audit, and would sail straight into the panel question "show me the trace for case #47."

### REQUIRED CHANGE

A first-class `decision_record`, written in the same transaction as arbitration, containing every number needed to reconstruct the choice. The explanation renderer is a **pure function of the record**. An LLM may phrase it, but may not supply any fact absent from the record — and for the prototype, template rendering is sufficient and safer.

### UPDATED DESIGN

```python
def render_explanation(rec: DecisionRecord) -> str:
    """Pure function of the record. No model call, no outcome data, no hindsight."""
    lines = [f"Customer {rec.customer_id} / opportunity {rec.opportunity_id}",
             f"policy {rec.policy_version} | model {rec.model_version}", ""]
    for c in sorted(json.loads(rec.candidate_actions),
                    key=lambda c: c["score"], reverse=True):
        mark = "SELECTED" if c["action"] == rec.selected_action else "rejected"
        lines.append(f"  {c['action']:<22} p={c['p_recovery']:.2f} "
                     f"E={rupees(c['expected_paise']):>10}  {mark}"
                     + ("" if c["eligible"] else f"  [blocked: {c['reason']}]"))
    lines += ["", f"Selected: {rec.selected_action} — {rec.selected_reason}"]
    return "\n".join(lines)
```

## P0.1-12 — FEEDBACK-LOOP DATA LEAKAGE

### CURRENT DESIGN

Feature list named (ageing, prior failures, stream, amount, channel history, relationship score) with no timestamp discipline; the technical review flags leakage as "must be checked."

### PROBLEM

`relationship_score` and `prior_recoveries` are trivially computable from data that only exists *after* the decision. In simulation there is a second, sharper leak: the generator's own payer parameters are sitting right there, and a model that reads them will look excellent and mean nothing.

### REQUIRED CHANGE

Point-in-time correctness, enforced by construction rather than by care:

- Every feature value carries `as_of`; the builder asserts `as_of <= decision_timestamp` for **all** features.
- Every label carries `observed_at`; training asserts `observed_at > decision_timestamp`.
- A **denylist** of fields that may never be featurised.
- **Generator ground-truth parameters are never exposed to the feature builder** — the simulator hands the engine an event view, not its internal state.
- Splits are ordered by time **and** grouped by customer, so one customer never straddles train and test.

### UPDATED DESIGN


## P0.1-14 — ABSTENTION

### CURRENT DESIGN

`final.md` F9 declares abstention as a first-class output and calls it "the highest-value output," but no arbitration or scoring structure carries it. P0-1's arbitration is `max(candidates, key=expected_value)` — with no abstain candidate, something is always chosen.

### PROBLEM

The safety thesis rests on abstention, and the code as written cannot abstain. It is also the honest answer to several panel questions, and cannot be demonstrated on camera unless it exists structurally.

### REQUIRED CHANGE

`ABSTAIN` is a permanent member of the candidate set with a defined score, and it **wins by default** whenever any trigger fires:

| Trigger | Condition | Reason code |
|---|---|---|
| Low confidence | `stage0_confidence < tau_risk` — cannot establish money was at risk | `unexplained_shortfall` |
| Ambiguous identity | `identity_match_confidence < tau_id` | `identity_unresolved` |
| Uncertain policy | any hard rule returns `unknown` rather than allow/block | `policy_indeterminate` |
| Unknown payment state | retry/payment state is `UNKNOWN` (P0.1-6) | `payment_state_unknown` |
| Negligible value | `max(expected_paise) < min_action_threshold_paise` | `below_value_threshold` |

The abstention **rate is reported for every arm**, including baselines — a rules engine's comparable is "no rule matched," and showing that contrast is what makes the claim in `final.md` §3.5 measurable rather than rhetorical.

### UPDATED DESIGN

```python
ABSTAIN = Candidate(action=ActionType.ABSTAIN, expected_paise=0, cost_paise=0,
                    score=0.0, eligible=True, reason="abstain_default")

def arbitrate(scope, customer_id, candidates, ctx, policy) -> Decision:
    triggers = abstention_triggers(ctx, policy)
    if triggers:
        return Decision(action=ActionType.ABSTAIN,
                        abstention_reason=triggers[0].code,
                        candidates=candidates + [ABSTAIN],
                        rejected=[(c, "abstained_" + triggers[0].code) for c in candidates])

    eligible = [c for c in candidates if policy.hard_check(scope, customer_id, c).allowed]
    pool = eligible + [ABSTAIN]
    winner = max(pool, key=lambda c: c.score)         # ABSTAIN wins if nothing beats zero
    if winner is ABSTAIN:
        return Decision(action=ActionType.ABSTAIN, abstention_reason="below_value_threshold", ...)
    return Decision(action=winner.action, ...)        # reservation happens only from here
```

**An abstention reserves nothing.** No budget slot is consumed, and the decision record still captures every candidate considered.

# 6. REMAINING RISKS

Honest, after all of the above is built.

1. **Everything is still a simulation.** A randomised design over synthetic data measures the simulator's payer-response function, not the world. The correct claim remains *relative* performance under an authored data-generating process. No architectural fix exists; the only mitigation is labelling, and repeating the label in the README, the video, and the results table.
2. **Simulation mode's counterfactual is computed, not observed.** It is defensible only because the world is authored. If any real Razorpay test-mode data enters the harness, simulation-mode numbers must not be reported alongside it as if they were the same kind of evidence.
3. **SQLite single-writer scopes the concurrency claim.** The 100-worker test demonstrates correctness under contention in one process against one file. It is not evidence about a distributed deployment, and should not be described as such.
4. **The ambiguous-send window is bounded, not closed.** A lost provider webhook leaves a slot held in `execution_unknown` indefinitely. Mitigation is a reconciliation job plus a manual review queue — a process, not a proof.
5. **Identity resolution remains the load-bearing input to D1 and is still heuristic.** Under-merging deflates D1's measured benefit; over-merging causes wrongful suppression. Both rates must be reported, and the confidence threshold published. This is the most likely source of a wrong headline number.
6. **The retry safety claim is now narrower.** With `RECOMMEND_RETRY`, the engine cannot cause a retry — good — but the project also can no longer claim end-to-end retry-cap enforcement. Say the narrower thing.
7. **The 4/month cap is still unjustified** until the 2/4/6/8 sensitivity sweep runs. Until then it is a stated placeholder, not a finding.
8. **Twenty seeds gives a CI on the mean, not on the tail.** Rare events — disputes, identity collisions, misclassified outages — are not characterised at this sample size.
9. **Four or five arms multiply the family-wise error rate.** Pre-register two primary comparisons (A2−A1 for D1/D3, A3−A2 for D2) and treat the rest as exploratory, or apply a correction. Do not report the best of five.
10. **The baselines are authored by the same team.** The freeze commit, the separate tuning seeds and the published parameters reduce this; they do not eliminate it.
11. **Last-touch attribution is a choice.** It is reported alongside first-touch, and the arm-level difference does not depend on it — but a reviewer may still argue the diagnostic.
12. **`CHECK` constraints protect the invariant only where the DB enforces them.** If any code path writes counters outside the ledger module, the guarantee is void. The credential/module isolation is enforced by a static test, which is weaker than a runtime boundary.
13. **Stage 0's probabilistic arm remains unfalsifiable against synthetic ground truth.** Only the statutory sub-checks (TDS, matching) have external truth; the rest is graded against the generator's own labels. Report the two separately, always.
