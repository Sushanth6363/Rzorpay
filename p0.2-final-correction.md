## FIX 1 — RESERVATION LIFECYCLE: COMPLETE TRANSITION TABLE

### CURRENT DESIGN

Four functions, each guarded by `AND status = 'reserved'`. `execution_unknown` is set by a bare `set_status()` call with no guard and no counter semantics.

### PROBLEM

R-1, R-2, R-3. The state exists but is unreachable in both directions: nothing legally enters it under a CAS, and nothing can leave it. `consumed_count` is incremented for a send that may never have happened.

### FIX

- `reserved_count` = **in flight or unconfirmed**. `consumed_count` = **permanently unavailable for reuse** — either confirmed sent, or failed closed after an unresolved execution. *(Superseded and refined by `p0.2-patch.md` FIX 1, which adds the `consumption_basis` column distinguishing `CONFIRMED_SENT` from `FAILED_CLOSED_UNRESOLVED`, and forbids reading `consumed_count` as "contacts sent".)* `execution_unknown` holds its slot in `reserved_count`. *(This corrects P0.1 test T8.3.)*
- Every transition is a CAS whose `WHERE` clause names the exact source state(s).
- Terminal states — `executed`, `released`, `expired`, `unresolved` — accept no further transitions; an attempt returns the current status and moves no counter.
- Invariant unchanged and still DB-enforced: `reserved_count + consumed_count <= cap`.

### UPDATED LOGIC

**Legal transitions.** Anything not listed is rejected.

| From | To | DB condition (added to `id = ? AND merchant_id = ?`) | Rows | Counter effect | Repeat call |
|---|---|---|---|---|---|
| — | `reserved` | `INSERT … ON CONFLICT (merchant_id, idempotency_key) DO NOTHING`, after `UPDATE … WHERE reserved+consumed < cap` | 1 | `reserved += 1` | returns the existing reservation; **no counter change** |
| `reserved` | `executed` | `AND status='reserved'` | 1 | `reserved -= 1`, `consumed += 1` | 0 rows → no-op, returns `True` |
| `reserved` | `released` | `AND status='reserved'` | 1 | `reserved -= 1` | 0 rows → no-op, returns `True` |
| `reserved` | `expired` | `AND status='reserved' AND expires_at < :now` | 1 | `reserved -= 1` | 0 rows → no-op |
| `reserved` | `execution_unknown` | `AND status='reserved'` | 1 | **none** (slot stays in `reserved`) | 0 rows → no-op |
| `execution_unknown` | `executed` | `AND status='execution_unknown'` | 1 | `reserved -= 1`, `consumed += 1` | 0 rows → no-op |
| `execution_unknown` | `released` | `AND status='execution_unknown'` | 1 | `reserved -= 1` | 0 rows → no-op |
| `execution_unknown` | `unresolved` | `AND status='execution_unknown' AND reconcile_attempts >= :max AND first_unknown_at < :now - 24h` | 1 | `reserved -= 1`, `consumed += 1` (**fail closed**) | 0 rows → no-op |

**Explicitly rejected** (CAS matches 0 rows, function returns current status, no counter moves, attempt is audited):

```
executed   -> released | expired | execution_unknown | reserved
released   -> executed | expired | execution_unknown | reserved
expired    -> executed | released | execution_unknown | reserved
unresolved -> anything
execution_unknown -> reserved | expired
```

```python
TERMINAL = {"executed", "released", "expired", "unresolved"}

LEGAL = {
    ("reserved",          "executed"):           (-1, +1),
    ("reserved",          "released"):           (-1,  0),
    ("reserved",          "expired"):            (-1,  0),
    ("reserved",          "execution_unknown"):  ( 0,  0),
    ("execution_unknown", "executed"):           (-1, +1),
    ("execution_unknown", "released"):           (-1,  0),
    ("execution_unknown", "unresolved"):         (-1, +1),
}

def transition(merchant_id, reservation_id, to_state, *, extra_sql="", params=(), clock):
    """Single entry point. Idempotent by construction: the CAS decides."""
    froms = [f for (f, t) in LEGAL if t == to_state]
    with db.transaction("BEGIN IMMEDIATE"):
        cur = db.one("SELECT status FROM contact_reservation WHERE id=? AND merchant_id=?",
                     (reservation_id, merchant_id))
        if cur is None:
            raise UnknownReservation(reservation_id)
        if cur["status"] == to_state:
            return TransitionResult(ok=True, changed=False, status=to_state)   # idempotent
        if (cur["status"], to_state) not in LEGAL:
            audit("illegal_transition_rejected", reservation_id, cur["status"], to_state)
            return TransitionResult(ok=False, changed=False, status=cur["status"])

        n = db.execute(f"""
            UPDATE contact_reservation
               SET status = ?, {timestamp_col(to_state)} = ?
             WHERE id = ? AND merchant_id = ?
               AND status IN ({placeholders(froms)}) {extra_sql}
        """, (to_state, clock.now_iso(), reservation_id, merchant_id, *froms, *params)).rowcount
        if n == 0:
            return TransitionResult(ok=True, changed=False, status=current(reservation_id))

        d_res, d_con = LEGAL[(cur["status"], to_state)]
        if (d_res, d_con) != (0, 0):
            db.execute("""
                UPDATE customer_month_budget
                   SET reserved_count = reserved_count + ?,
                       consumed_count = consumed_count + ?,
                       version = version + 1
                 WHERE (merchant_id, customer_id, month) =
                       (SELECT merchant_id, customer_id, month
                          FROM contact_reservation WHERE id = ?)
            """, (d_res, d_con, reservation_id))
        return TransitionResult(ok=True, changed=True, status=to_state)
```

All four public functions become thin wrappers, so no counter arithmetic exists anywhere else in the codebase.

## FIX 2 — `EXECUTION_UNKNOWN` RECONCILIATION

### CURRENT DESIGN

On an ambiguous provider response the reservation is parked in `execution_unknown` and a reconciliation job is enqueued. Neither the job nor its termination is defined.

### PROBLEM

The invariant the state exists to protect — *never double-contact, never permanently consume a slot without an observable resolution path* — is currently satisfied only in its first half. The slot is held indefinitely and nothing observes it.

### FIX

A bounded reconciliation ladder with a **terminal, fail-closed, reported** outcome.

```
                    RESERVED
                        |
              ambiguous provider response
                        v
              EXECUTION_UNKNOWN  (slot held in reserved_count)
                        |
          reconcile at 1m, 5m, 30m, 2h, 6h, 24h
                        |
        +---------------+----------------+------------------+
        |               |                |                  |
   DELIVERED /      NOT_SENT /       still unknown      provider says
   SENT             REJECTED         after 24h          "never existed"
        |               |                |                  |
        v               v                v                  v
    EXECUTED        RELEASED        UNRESOLVED           RELEASED
  reserved-1        reserved-1      reserved-1          reserved-1
  consumed+1                        consumed+1
                                    + human queue
                                    + metric
```

Rules:

1. **Never re-send.** The reservation is not re-executable from `execution_unknown`; the executor refuses it. This is the anti-double-contact guarantee, and it is structural, not procedural.
2. **`UNRESOLVED` counts as consumed.** If we cannot prove the message did not go out, we assume it did. Fail-closed protects the customer at the cost of one possibly-wasted slot.
3. **`UNRESOLVED` is never silent.** Every occurrence lands in a human review queue and is reported as `unresolved_execution_rate` in the results table alongside the harm metrics. A non-zero number here is more credible than a suppressed one.
4. **The prototype uses a synthetic provider** that can be told to return `delivered`, `not_sent`, `ambiguous-then-delivered`, `ambiguous-then-not_sent`, or `never responds`.

### UPDATED LOGIC

```sql
ALTER TABLE contact_reservation ADD COLUMN first_unknown_at      TEXT;
ALTER TABLE contact_reservation ADD COLUMN reconcile_attempts    INTEGER NOT NULL DEFAULT 0;
ALTER TABLE contact_reservation ADD COLUMN provider_ref          TEXT;
ALTER TABLE contact_reservation ADD COLUMN resolution_source     TEXT;
   -- provider_webhook | provider_poll | timeout_failclosed | provider_unknown_ref
```

```python
RECONCILE_LADDER_MINUTES = (1, 5, 30, 120, 360, 1440)

class DeliveryStatus(str, Enum):
    DELIVERED = "delivered"; NOT_SENT = "not_sent"
    UNKNOWN = "unknown";     NO_SUCH_REF = "no_such_ref"

def reconcile_unknown(merchant_id, clock, provider) -> ReconcileReport:
    rows = db.all("""SELECT id, provider_ref, first_unknown_at, reconcile_attempts
                       FROM contact_reservation
                      WHERE merchant_id=? AND status='execution_unknown'""", (merchant_id,))
    for r in rows:
        if not due(r, RECONCILE_LADDER_MINUTES, clock):
            continue
        status = provider.check(r["provider_ref"]) if r["provider_ref"] else DeliveryStatus.UNKNOWN

        if status is DeliveryStatus.DELIVERED:
            transition(merchant_id, r["id"], "executed", clock=clock)
            set_resolution(r["id"], "provider_poll")
        elif status in (DeliveryStatus.NOT_SENT, DeliveryStatus.NO_SUCH_REF):
            transition(merchant_id, r["id"], "released", clock=clock)
            set_resolution(r["id"], "provider_poll")
        else:
            bump_attempts(r["id"])
            if elapsed(r["first_unknown_at"], clock) >= hours(24):
                transition(merchant_id, r["id"], "unresolved",
                           extra_sql=" AND reconcile_attempts >= ? AND first_unknown_at < ?",
                           params=(len(RECONCILE_LADDER_MINUTES), clock.minus_hours_iso(24)),
                           clock=clock)
                set_resolution(r["id"], "timeout_failclosed")
                human_queue.push(r["id"], reason="unresolved_execution")
                metrics.increment("unresolved_execution")
```

A provider delivery **webhook** takes the same path (`transition(...)`), so webhook and poll cannot race into different outcomes — whichever arrives first wins the CAS, the second is a no-op.

## FIX 5 — STATISTICAL CLAIM DISCIPLINE

### CURRENT DESIGN

"≥20 seeds, report mean and CI."

### PROBLEM

No stated estimator, no interval method, no power analysis (R-6), no multiplicity handling (R-7), no rule for what to say when the interval includes zero.

### FIX

**Estimators.** Unit of analysis = the randomisation unit (simulation: the seed; randomised: the customer).

```
absolute lift  = mean_T(recovered_paise per eligible opportunity)
               - mean_C(recovered_paise per eligible opportunity)

relative lift  = mean_T / mean_C          (reported only WITH a bootstrap CI)

rate lift      = P_T(recovered) - P_C(recovered)
```

**Interval methods** — stated per metric, not chosen after seeing the data:

| Metric | Method | Why |
|---|---|---|
| Recovered paise / opportunity (simulation) | paired t-interval on per-seed differences, n = seeds | arms see identical data; pairing removes between-seed variance |
| Recovered paise / opportunity (randomised) | Welch t-interval on per-customer means | unequal variance, unequal n |
| Recovery rate (proportion) | Newcombe interval for the difference of two proportions | correct near 0 and 1 |
| Relative lift | BCa bootstrap over the randomisation unit, 10,000 resamples | ratio of means is skewed |
| Direction check | Wilcoxon signed-rank (paired) / Mann-Whitney (unpaired) | ₹ per batch is right-skewed |
| Paired proportions (false-contact, phantom removal) | McNemar | paired binary |

**Power, computed before the run, not after:**

```python
def minimum_detectable_effect(pilot_seeds=5, n_seeds=40, alpha=0.05, power=0.80):
    d  = paired_differences(run_pilot(pilot_seeds))
    sd = stdev(d)
    return (t_crit(alpha/2, n_seeds-1) + t_crit(1-power, n_seeds-1)) * sd / sqrt(n_seeds)
```

Run 5 pilot seeds, compute the MDE, **publish it**, and choose `n_seeds` so the MDE sits below the effect worth claiming. If the observed effect lands below the MDE, the honest report is "below this experiment's resolution," not "no effect."

**Multiplicity.** One primary comparison, uncorrected. The secondary family of three gets Holm–Bonferroni; both raw and adjusted p-values are printed.

**Reporting template — every delta, no exceptions:**

```
Unified Recovery Engine lift (A2 - A1)
  absolute:  +Rs 412 per eligible opportunity   95% CI [Rs 96, Rs 728]
  relative:  +14.2%                             95% CI [3.1%, 26.0%]   (BCa bootstrap)
  n = 40 seeds x 600 opportunities;  paired t-interval;  MDE at n=40: Rs 250
  guardrails: false-contact 0.0% | contacts/customer 1.9 | unresolved-exec 0.4%
```

**The inconclusive rule.** If the interval includes zero:

> *"The difference is inconclusive at this sample size (95% CI [a, b], MDE = m). This is not evidence of no effect."*

Never "trending positive," never "directionally better," never significance claimed from having run many seeds.

## FIX 6 — STAGE 0 CIRCULARITY

### CURRENT DESIGN

"Stage-0 accuracy vs ground truth" reported as a headline metric (`final.md` §4, metric 6).

### PROBLEM

For every probabilistic sub-check, the generator writes the label and the validator is graded against it. If both derive from the same rule, accuracy measures whether the pipeline is wired up — not whether the check works.

### FIX

Split Stage 0's reporting into two tables that never merge into one number.

**Deterministic — externally checkable, real ground truth:**

| Check | Truth source |
|---|---|
| TDS withholding at a statutory rate | statutory rate table (external) |
| Payment↔invoice reference match | transaction records |
| Duplicate payment | transaction records |
| Already-settled invoice | transaction records |
| Explicit subscription cancellation (recorded signal) | cancellation record |
| Known payment status | processor status |

**Probabilistic — graded against synthetic ground truth only:**

| Check | Truth source |
|---|---|
| Customer already self-cured (inferred) | generator's authored label |
| Cart completed elsewhere | generator's authored label |
| Deliberate vs accidental cancellation (inferred) | generator's authored label |
| Likely responsiveness / recoverability | generator's authored label |

**Required label, on the slide and in the README:**

> **Synthetic ground truth.** The probabilistic Stage 0 checks are evaluated against labels this project's own generator produced. That measures pipeline correctness — that a case labelled *not at risk* is not contacted — and **not** real-world accuracy. Only the deterministic checks are graded against an external source (the statutory rate table). No real-world Stage 0 accuracy is claimed.

Two anti-circularity requirements:

1. **The generator's labelling rule and the validator's decision rule must not share code.** They are separate modules with a test asserting no import path between them.
2. **The generator injects adversarial cases** the validator has no rule for — boundary TDS rates, cancellations with mixed signals, self-cures just outside the window. The validator is expected to **abstain**, and the abstention rate on adversarial cases is reported. A validator that never abstains on them has memorised the generator.

### UPDATED LOGIC

```python

    check: str
    confidence: float

    return {
      "deterministic": accuracy_table([r for r in results if r.basis == "deterministic"]),
```

## FIX 8 — ABSTENTION, FINALISED

### CURRENT DESIGN

Five triggers from P0.1: low Stage 0 confidence, ambiguous identity, indeterminate policy, unknown payment state, below value threshold.

### PROBLEM

Two conditions from the brief are missing, and one of them — recent contact — is not modelled anywhere. The monthly cap is not a cooldown: a customer can legally receive contacts 2, 3 and 4 on three consecutive days and stay inside the cap.

### FIX

Seven triggers, evaluated in order; the first to fire wins and is recorded.

| # | Trigger | Condition | Reason code |
|---|---|---|---|
| 1 | Low confidence | `stage0_confidence < tau_risk` | `unexplained_shortfall` |
| 2 | Ambiguous identity | `identity_confidence < tau_id` | `identity_unresolved` |
| 3 | Policy uncertainty | any hard rule returns `unknown` | `policy_indeterminate` |
| 4 | Unknown payment state | retry/payment state `UNKNOWN` | `payment_state_unknown` |
| 5 | **Recent contact (NEW)** | `hours_since_last_contact < cooldown_hours` (default 72) | `contact_cooldown` |
| 6 | **Communication cost (NEW)** | `expected_paise - channel_cost_paise < min_margin_paise` | `cost_exceeds_benefit` |
| 7 | Negligible value | `max(expected_paise) < min_action_threshold_paise` | `below_value_threshold` |

`cooldown_hours` is a separate policy parameter from the monthly cap and is swept alongside it (24/72/168) in the sensitivity analysis.

**An abstention reserves nothing** — no budget slot, no cooldown consumption — and still writes a full decision record.

**Reported metrics** (per arm, in the results table):

```
abstention_rate                      = abstained / eligible opportunities
abstention_rate_by_reason            = breakdown across the 7 codes
recovery_rate_among_non_abstained    = recovered / acted-upon
false_contact_rate                   = contacted where money was not at risk
wrongly_suppressed_rate              = abstained/suppressed but the case
                                       resolved for another arm that did act
```

The last one is the honest counterweight the PM review asked for: the cost of abstaining, reported next to its benefit.

**Objective statement, in the README:** the engine optimises *recovered revenue subject to harm guardrails*, not intervention count. Contact reduction is a guardrail, never the headline.

## FIX 9 — FEEDBACK LOOP, MADE REAL

### CURRENT DESIGN

Online/offline split and `model_registry` defined; no run exercises them.

### PROBLEM

R-10 and R-11. The loop is undemonstrated, and — more seriously — outcomes exist only for actions v1 actually chose. Training v2 on that log is learning from a self-selected sample, and the promotion gate inherits the bias.

### FIX

**Add a small exploration holdout.** In `A5` only, a fixed fraction (`epsilon = 0.05`) of policy-eligible opportunities receive a **uniformly random choice among policy-eligible actions** instead of the argmax. Selection is deterministic: `explore = hash(experiment_id | opportunity_id) % 100 < 5`. Explored decisions are flagged `is_exploration=True` and carry `propensity = 1/len(eligible)`; argmax decisions carry their own propensity for later inverse-propensity weighting.

Exploration never violates safety: it selects only among **already policy-cleared** actions, respects the budget and cooldown, and can still land on `ABSTAIN`.

**The demonstration run** (one concrete pass, not a pipeline claim):

```
v1  trained offline on tuning seeds 1-10
      |
run A5 on evaluation seeds 21-40 with v1 PINNED  (epsilon = 0.05)
      |
outcomes classified by the P0.1-3 timeline rules
      |
point-in-time dataset built (feature.as_of <= decision_timestamp)
   + propensity column, exploration flag
      |
v2 trained on that dataset
      |
offline evaluation on HELD-OUT tuning seeds 11-20 (never used for either model)
      |
PROMOTION GATE - all four must pass:
   1. Brier(v2) < Brier(v1)
   2. calibration slope in [0.9, 1.1]
   3. AUC(v2) >= AUC(v1) - 0.01
   4. replayed false-contact rate not worse than v1
      |
   pass -> promote, registry row, pointer moves
   fail -> reject, reason recorded, v1 stays active
      |
rollback exercised explicitly; decisions stay stamped with what actually ran
```

**No online retraining.** The model artefact hash is constant for the whole of any evaluation run (P0.1-13 invariant, retained).

# 5. UPDATED AI EVALUATION

**The question:** why does this need an AI decision layer instead of deterministic rules?

**The experiment:** A5 vs A3 — same engine, same features, same candidates, same policy, same budget, same payment state, paired across 40 evaluation seeds. Only `ActionScorer` differs.

| Metric | A3 (heuristic) | A5 (model) | Δ, 95% CI |
|---|---|---|---|
| Recovery rate | | | |
| Recovered ₹ / eligible opportunity | | | |
| Contact efficiency (₹/contact) | | | |
| False-contact rate *(guardrail)* | | | |
| Abstention rate | | | |
| Brier score | | | |
| Calibration slope | | | |
| Top-k EV vs oracle | | | |

**Pre-committed reading of the result:**

- **CI entirely above zero** → the model measurably improves action selection *on this synthetic batch*. Report the magnitude; repeat the synthetic caveat.
- **CI includes zero** → say plainly: *the model does not measurably outperform the heuristic scorer here.* The case for the AI layer then rests on three separately-measured capabilities, not on the scorer:
  1. calibrated abstention — abstention precision on adversarial Stage 0 cases;
  2. open-hypothesis diagnosis — share of residual cases the heuristic cannot classify;
  3. cross-case correlation — cluster precision on injected outages.
- **CI entirely below zero** → the heuristic wins. Ship it as the default scorer and say so on camera.

**Stated limitation:** the payer-response function is authored by this project. A5 vs A3 compares how well two scorers approximate a known function. It is not evidence about real-world model value, and the README says exactly that.

**Calibration is a gate, not a metric.** Stage 2 multiplies value by probability; if `p` is uncalibrated the EV ranking is arbitrary. Brier and calibration slope are reported before any EV-based claim is made.

# 6. UPDATED FEEDBACK LOOP

```
ONLINE  (inside a run)                    OFFLINE (between runs)
--------------------------------------    --------------------------------------
inference, model hash PINNED              point-in-time dataset construction
customer-state update                     training
outcome logging (+ propensity, epsilon)   validation, calibration
audit / trace writes                      offline comparison vs incumbent
                                          promotion decision, rollback
```

**Concrete demonstration, run once as `make feedback-demo`:**

```
v1 = train(tuning seeds 1-10)
  -> pin v1, run A5 on evaluation seeds 21-40 with epsilon = 0.05 exploration
  -> classify outcomes (P0.1-3 timeline rules)
  -> build point-in-time dataset (feature.as_of <= decision_timestamp; propensity recorded)
  -> v2 = train(that dataset)
  -> offline evaluation on held-out seeds 11-20
  -> PROMOTION GATE (all four must pass):
        Brier(v2) < Brier(v1)
        calibration slope in [0.9, 1.1]
        AUC(v2) >= AUC(v1) - 0.01
        replayed false-contact rate not worse
  -> promote (registry row + pointer move) or reject (reason recorded)
  -> rollback exercised; decisions remain stamped with what actually ran
```

**Why exploration is mandatory, not optional:** without it, v2 trains only on actions v1 chose. The 5% uniform-random-among-eligible holdout gives the training set unbiased coverage and supplies the propensities needed for inverse-propensity weighting. It never violates a policy constraint, a budget, or a cooldown — it chooses among already-cleared actions, and `ABSTAIN` remains a legal draw.

**No continuous online retraining.** The artefact hash is invariant within a run.
