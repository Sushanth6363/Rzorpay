# 1. STATISTICAL POWER

## Prototype objective vs production objective

| **What this prototype sets out to demonstrate** | **What a production claim would require** |
|---|---|
| the experimental infrastructure runs | substantially larger sample sizes |
| results are reproducible from a seed and a reference timestamp | real payer behaviour |
| causal-comparison mechanics are correct (identical inputs, one flag differing per comparison) | real recovery outcomes |
| model-selection governance holds (training / selection / holdout stay separated) | production-calibrated models |
| the feedback loop is intact (train → evaluate → gate → promote → roll back) | a proper power analysis on real variance |
| the safety invariants hold (budget, idempotency, abstention, tenant isolation) | production traffic and real merchants |

**This prototype's experiment is an architecture test, not an efficacy trial.** It asks whether the engine behaves correctly and measurably differently from a baseline under conditions this project controls. It does not ask, and cannot answer, whether that difference exists for real merchants.

## What the sample size can and cannot support

**Unit of randomisation is the seed, not the opportunity.** In simulation mode all arms see the same 600 opportunities per seed, so the independent replicates number **40** (`EXPERIMENT_SET`), not 24,000. Reporting n = 24,000 would be a false-precision claim, and any interval computed at that n is wrong.

Two consequences, and they pull in opposite directions:

1. **Pairing with common random numbers makes the comparison unusually precise.** Because every arm faces the identical opportunity set and the identical RNG draws, between-seed variance cancels in the paired difference. Effects that are systematic and near-deterministic — contact suppression under a shared budget, retry suppression during a modelled outage — will be detectable at 40 seeds with narrow intervals.
2. **That precision is precision about the simulator.** A tight confidence interval here bounds sampling error under an authored data-generating process. It says nothing about how far the estimate sits from the real-world value, and no sample size fixes that. The dominant error term is the model of payer behaviour, and it has no confidence interval at all.

**Stated plainly, for the README:**

> The 40-seed paired design is sufficient to detect systematic architectural differences and to report their intervals under the synthetic data-generating process. It is **not** sufficient to establish that a modest recovery-rate difference would hold for real merchants, and no sample size drawn from this generator could establish that. Reported intervals quantify sampling error within the simulation only.

## Power calculation — assumptions, or nothing

No power calculation is presented here, because the standard deviation of paired per-seed differences is unknown until the pilot runs. Manufacturing one from assumed values would be a worse error than omitting it.

The calculation **will** be run, from the 5-seed pilot, and published with every assumption stated:

```
minimum detectable effect (paired design)

MDE = (t_{1-alpha/2, n-1} + t_{power, n-1}) * SD_paired_diff / sqrt(n)

assumptions to be filled from the pilot and stated verbatim in the results:
  baseline recovery rate .......... measured on A1, INITIAL_TRAINING_SET  [pilot output]
  SD of paired differences ........ measured across 5 pilot seeds         [pilot output]
  minimum detectable effect ....... derived, not assumed
  alpha ........................... 0.05, two-sided
  power ........................... 0.80
  allocation ratio ................ 1:1 (paired; every arm sees every seed)
  unit of randomisation ........... seed (simulation mode), n = 40
```

If the observed effect falls below the computed MDE, the report says **"below this experiment's resolution"** — never "no effect", never "trending".

If the pilot shows the SD is large enough that 40 seeds cannot resolve the primary comparison, the honest options are to raise the seed count (seeds are cheap) or to report the comparison as underpowered. Both are acceptable; quietly reporting a wide interval as a result is not.

# 2. PRIMARY METRIC

**One primary metric. Everything else is secondary and labelled as such.**

```
PRIMARY METRIC

Incremental Recovery Rate
=
Treatment Recovery Rate  -  Control Recovery Rate

evaluated at the unit of randomisation (seed in simulation mode),
for the primary comparison A2 vs A1
```

Recovery rate is chosen over recovered revenue as the primary because rupee amounts are heavily right-skewed at this batch size, which makes revenue the noisier estimator. Rate is the more stable statistic and therefore the more honest primary.

**Secondary metrics** — reported with intervals, never promoted to the headline:

```
incremental recovered revenue          (rupees; the Track 3 bar names money - see below)
revenue per contact
contacts per customer
false-contact rate                     [guardrail]
abstention rate
downtime-induced retry suppression
phantom-risk value avoided             (Stage 0; never called "recovered")
wrongly-suppressed rate                [guardrail]
unresolved-execution rate              [guardrail]
```

**On the revenue number.** Track 3's brief names *money recovered across a batch*, so incremental recovered revenue is reported with equal visual prominence in the results table — but it is labelled **secondary and higher-variance**, and the statistical verdict (significant / inconclusive / below resolution) is taken from the primary rate metric. Two numbers, one verdict.

**Anti-drift rule:** the results renderer marks exactly one metric `primary: true`. A build in which zero or more than one metric carries that flag fails.

```python
def test_exactly_one_primary_metric():
    flagged = [m for m in report().metrics_meta if m.primary]
    assert len(flagged) == 1
    assert flagged[0].name == "incremental_recovery_rate"
    assert flagged[0].comparison == "A2_vs_A1"

def test_secondary_metrics_never_carry_the_verdict():
    assert report().verdict_source == "incremental_recovery_rate"
```

*(This supersedes the earlier primary metric `recovered_paise_per_eligible_opportunity`. The change is made before any evaluation run and is written into the pre-registration file, which is git-tagged before the first run.)*

# 3. RECOVERY RATE VS RECOVERED REVENUE

Four terms, four definitions, never interchangeable.

```
Recovery Rate
= number of eligible opportunities recovered
  / number of eligible opportunities

Recovered Revenue
= sum of recovered monetary value (integer paise)

Incremental Recovered Revenue
= Treatment recovered revenue - Control recovered revenue
  (as a difference of per-unit means, then extrapolated with a CI;
   never a difference of raw totals when arm sizes differ)

Revenue per Contact
= recovered revenue / confirmed contacts
  where confirmed contacts = COUNT(status = 'executed')
  -- NOT consumed_count, which also includes failed-closed unresolved slots
```

**Eligibility** is fixed once and applies identically to every arm: an opportunity is eligible if it was not closed by Stage 0 as never-at-risk. Opportunities Stage 0 closes are excluded from both the numerator and the denominator of recovery rate, and their value is reported separately as *phantom-risk value avoided*.

```python
def test_recovery_rate_denominator_is_identical_across_arms():
    d = {a: eligible_count(a) for a in ARMS}
    assert len(set(d.values())) == 1        # Stage 0 differences must not shift the denominator

def test_revenue_per_contact_uses_confirmed_contacts():
    r = report()
    assert r["revenue_per_contact"] == r["recovered_revenue"] / r["contacts_confirmed"]

def test_the_four_terms_are_separate_fields():
    for k in ["recovery_rate", "recovered_revenue",
              "incremental_recovered_revenue", "revenue_per_contact"]:
        assert k in report()
```

# 4. SELF-CURE DISTINCTION PRESERVED

Three outcome classes remain distinct in the data model, in every metric, and in the demo narration:

| Class | Definition | Counts toward the intervention effect? |
|---|---|---|
| `SELF_CURED` | payment occurred **before** the first delivered intervention, or no intervention was ever delivered | **No — never, under any window** |
| `RECOVERED_ATTRIBUTED` | payment occurred within the attribution window after a delivered intervention | Yes |
| `RECOVERED_UNATTRIBUTED` | payment occurred inside the observation window but outside every attribution window | Reported separately; never claimed as intervention-caused |

**The rule, stated in the evaluation methodology:**

> The system never claims a customer recovered because of an intervention if the customer had already paid before that intervention was delivered. Ordering is checked against delivery timestamps, not send timestamps, and the check precedes every attribution window test.

Self-cure rate is computed for **every arm**. Because all arms face identical seeded data, a material difference in self-cure rate between arms indicates a broken harness rather than a result — it is a validity check, and it is reported as one.

```python
def test_payment_before_delivery_is_never_attributed():
    o = opp(created="T0"); pay("T0+1h"); deliver("T0+2h")
    r = classify(o)
    assert r.status is OutcomeStatus.SELF_CURED and r.decision_id is None

def test_self_cure_excluded_from_incremental_effect():
    e = incremental_effect(outcomes, EXP)
    assert e.numerator_excludes(OutcomeStatus.SELF_CURED)

def test_self_cure_rate_agrees_across_arms():
    rates = {a: self_cure_rate(a) for a in ARMS}
    assert max(rates.values()) - min(rates.values()) < 0.02
```

# 5. AI VS HEURISTIC CLAIM — FINAL WORDING

`A5 vs A3` is described, everywhere, as:

> **AI scorer contribution under the project's synthetic response function.**

Never as production AI recovery improvement.

**The sentence that must appear in the submission, verbatim:**

> A result of *CatBoost > heuristic* means the CatBoost scorer better captured the response relationship represented by the synthetic data-generating process. It does **not** mean CatBoost has been proven superior for Razorpay's production customers. The response function was authored by this project; the comparison measures how well two scorers approximate it, on identical inputs.

If the interval includes zero, the submission says plainly that the model did not measurably outperform the heuristic here, and the argument for the AI layer rests on three separately-measured capabilities — abstention precision on adversarial cases, residual-case share the heuristic cannot classify, and correlation-cluster precision.

# 9. KNOWN PROTOTYPE LIMITATIONS

| # | Limitation | Why it matters | What the prototype still demonstrates | What production would require |
|---|---|---|---|---|
| 1 | **Synthetic payer-response data** | Every recovery number describes an authored world; the dominant error term is the response model, and it carries no interval | That the pipeline produces correct, reproducible, fairly-compared measurements — and that architectures can be ranked under a controlled process | Real recovery outcomes from live traffic, and a response model fitted rather than authored |
| 2 | **Limited experimental sample size** | 40 seeds bounds sampling error inside the simulation only; it cannot establish that a modest difference holds outside it | Precise, paired, reproducible comparisons with published intervals and a computed MDE | Power analysis on observed production variance, and a sample sized to the effect worth detecting |
| 3 | **Synthetic payment provider** | Delivery, ambiguity and outage signals are simulated, so real provider failure modes are unobserved | That every modelled failure path — ambiguous send, never-responds, duplicate webhook — resolves correctly and never double-contacts | Integration against real provider webhooks with reconciliation against their delivery status |
| 4 | **Prototype database and concurrency model** | SQLite single-writer scopes the concurrency claim to one process and one file | That the budget invariant holds under concurrent fuzzing, and that the transaction design is correct at prototype scale | Postgres with row-level security, arbitration partitioned by customer, and load testing at production concurrency |
| 5 | **No production Razorpay credential access** | The Downtime API is support-gated; retry attempt history is unverified | That the engine consumes the published downtime taxonomy and fails closed when payment state is unknown | Granted API access, and verification of the retry-state contract before any retry coordination claim |
| 6 | **Stage 0 probabilistic validation cannot establish real-world accuracy** | The generator writes the labels the validator is graded against | Pipeline correctness — that a case classified *not at risk* is never contacted — plus deterministic checks graded against an external statutory table | Labelled real shortfall cases, and accuracy measured against merchant-confirmed outcomes |
| 7 | **Identity resolution is modelled rather than production-scale** | D1 depends on it entirely: under-merging deflates the measured benefit, over-merging causes wrongful suppression | That resolution runs merchant-scoped, fails toward treating identities as distinct, and reports both error directions | Entity resolution against real customer records, with a measured merge-error rate |

**These are limitations of scope, not defects of design.** Each has a mechanism and a test behind it; none is unaddressed. A submission that states its own evidential limits is more useful to a reviewer than one that overstates and is found out in the Q&A.
