## FIX 1 — `consumed_count` SEMANTICS

### CURRENT

`consumed_count` is documented as "confirmed sent." The `EXECUTION_UNKNOWN → UNRESOLVED` path increments it.

### ISSUE

Those two statements contradict each other. An `UNRESOLVED` execution is precisely the case where delivery *cannot* be confirmed, yet it lands in a counter whose name asserts confirmation. Any metric reading `consumed_count` as "contacts sent" therefore overstates confirmed sends by the unresolved rate — silently, and in the direction that flatters the project.

### EXACT FIX

Redefine the counter by its **capacity meaning**, not its delivery meaning, and carry the delivery meaning in a separate audit column.

```
AVAILABLE CONTACT CAPACITY = cap - reserved_count - consumed_count
```

> **`consumed_count`** — contact slots permanently unavailable for reuse, because the contact was **confirmed as sent** *or* the system **failed closed after an unresolved execution**.

**Why an unresolved execution consumes the slot despite unconfirmed delivery:** the system cannot safely reuse the slot, because reuse could cause duplicate customer contact. Fail-closed costs at most one wasted slot; fail-open costs a duplicate message to a real person.

The delivery fact is preserved in `consumption_basis`:

```
CONFIRMED_SENT              -- provider confirmed delivery or acceptance
FAILED_CLOSED_UNRESOLVED    -- reconciliation exhausted; delivery unknown
```

**Metric consequence — binding on every report:** `contacts_sent` is `COUNT(status='executed')`, never `consumed_count`. Harm-side claims use the pessimistic bound.

```
contacts_confirmed = COUNT(status = 'executed')
contacts_possible  = COUNT(status IN ('executed','unresolved'))   -- upper bound
unresolved_rate    = COUNT(status='unresolved') / COUNT(reservations)
```

Efficiency metrics (₹ per contact) use `contacts_confirmed`. Harm metrics (contacts per customer, contacts saved vs baseline) use `contacts_possible`, so an unresolved send is never quietly counted in the project's favour.

Invariant unchanged: `reserved_count + consumed_count <= cap`.

### UPDATED LOGIC

```python
AVAILABLE = lambda b: b.cap - b.reserved_count - b.consumed_count

CONSUMPTION_BASIS = {
    "executed":   "CONFIRMED_SENT",
    "unresolved": "FAILED_CLOSED_UNRESOLVED",
}
# set inside the same transaction as the counter movement, never separately
```

```sql
ALTER TABLE contact_reservation ADD COLUMN consumption_basis TEXT;
   -- NULL unless status IN ('executed','unresolved')

-- guard: consumption_basis must agree with status
CREATE TRIGGER trg_consumption_basis
AFTER UPDATE OF status ON contact_reservation
WHEN NEW.status IN ('executed','unresolved')
  AND (NEW.consumption_basis IS NULL
       OR NEW.consumption_basis <> CASE NEW.status
             WHEN 'executed'   THEN 'CONFIRMED_SENT'
             ELSE 'FAILED_CLOSED_UNRESOLVED' END)
BEGIN SELECT RAISE(ABORT, 'consumption_basis inconsistent with status'); END;
```

## FIX 3 — FEEDBACK-LOOP DATASET TERMINOLOGY

### CURRENT

Seeds 21–40 are called "evaluation seeds" and are then used to train v2. Seeds 11–20 are called a holdout and are also used for the promotion decision.

### ISSUE

Two contradictions. A set cannot be both evaluation and training data under one name. And a set used to *decide* promotion is a validation set — using it repeatedly across candidate models leaks into the reported number, which is exactly what the brief forbids ("never used for … model promotion decisions").

### EXACT FIX

Four explicit roles. The brief's 11–20 holdout is split so the promotion decision and the reported number use different data — cheap, since seeds cost nothing.

| Role | Seeds | Used for | Never used for |
|---|---|---|---|
| `INITIAL_TRAINING_SET` | 1–10 | train v1; tune the heuristic scorer (equal effort) | any reported comparison |
| `MODEL_SELECTION_SET` | 11–15 | the promotion gate: v2 vs v1 | training, reported numbers |
| `FINAL_HOLDOUT_SET` | 16–20 | touched **once**, after promotion is decided, to report the number | training, feature selection, thresholds, hyperparameters, promotion |
| `EXPERIMENT_SET` | 21–60 (n=40) | the A1–A5 arm comparisons, run with v1 **pinned**; its outcomes are the `MODEL_UPDATE_SET` that trains v2 | evaluating v2 |

`EXPERIMENT_SET` legitimately serves both purposes because v1 never saw it: it is out-of-sample for the arm comparisons, and it becomes training data only for v2 — which is then never evaluated on it.

**Enforcement, not convention.** The final holdout is behind a gate object that refuses to reveal outcomes until promotion has been decided:

```python
class HoldoutGate:
    def __init__(self, seeds): self._seeds = seeds; self._unlocked = False
    def unlock(self, promotion_decision: PromotionDecision):
        assert promotion_decision.is_final, "holdout unlocked before promotion was decided"
        assert promotion_decision.selection_set == "MODEL_SELECTION_SET"
        self._unlocked = True
    def outcomes(self):
        if not self._unlocked:
            raise HoldoutLocked("FINAL_HOLDOUT_SET is unavailable before model selection")
        return load(self._seeds)
```

**Required disclosure**, because every set comes from one generator:

> All four dataset roles are drawn from the same synthetic data-generating process. This demonstrates **pipeline mechanics and temporal integrity** — that training, selection and reporting data stay separated, and that no future information reaches a past decision. It does **not** demonstrate generalisation to real payer behaviour.

### UPDATED LOGIC

```
INITIAL_TRAINING_SET (1-10)
        |
     Model v1
        |
     v1 evaluated on FINAL_HOLDOUT_SET (16-20)   [locked: recorded, not looked at]
        |
     run A1-A5 on EXPERIMENT_SET (21-60), v1 PINNED, epsilon = 0.05
        |
     collect outcomes  ->  MODEL_UPDATE_SET
        |
     Model v2
        |
     v2 vs v1 on MODEL_SELECTION_SET (11-15)
        |
     PROMOTION GATE  ->  promote | reject   (decision is final here)
        |
     HoldoutGate.unlock(decision)
        |
     v_promoted evaluated ONCE on FINAL_HOLDOUT_SET (16-20)  ->  reported number
```

# 2. UPDATED STATE MACHINE

Contact-reservation states only.

```
                         (no reservation)
                                |
                      reserve()  |  UPDATE ... WHERE reserved + consumed < cap
                                v
                          +------------+
                          |  RESERVED  |   reserved +1
                          +------------+
                           /    |    \  \
             confirmed    /     |     \  \  ambiguous provider response
             delivery    /      |      \  \
                        v       v       v  v
              +----------+ +----------+ +---------+ +---------------------+
              | EXECUTED | | RELEASED | | EXPIRED | | EXECUTION_UNKNOWN   |
              +----------+ +----------+ +---------+ +---------------------+
               res -1        res -1       res -1      res  0   con  0
               con +1        con  0       con  0      (slot still held in reserved)
               TERMINAL      TERMINAL     TERMINAL             |
               CONFIRMED_    capacity     capacity     +-------+--------+--------+
               SENT          returned     returned     |       |                 |
                                                  delivered  not_sent      ladder exhausted
                                                       |       |                 |
                                                       v       v                 v
                                                 EXECUTED  RELEASED        +------------+
                                                 res -1    res -1          | UNRESOLVED |
                                                 con +1    con  0          +------------+
                                                                            res -1 con +1
                                                                            TERMINAL
                                                                            FAILED_CLOSED_
                                                                            UNRESOLVED
```

| State | Terminal | `reserved_count` | `consumed_count` | `consumption_basis` | Capacity effect |
|---|---|---|---|---|---|
| `RESERVED` | no | **+1** | 0 | NULL | held (in flight) |
| `EXECUTED` | yes | **−1** | **+1** | `CONFIRMED_SENT` | permanently consumed |
| `RELEASED` | yes | **−1** | 0 | NULL | **returned** |
| `EXPIRED` | yes | **−1** | 0 | NULL | **returned** |
| `EXECUTION_UNKNOWN` | no | 0 | 0 | NULL | **still held** in `reserved_count` |
| `UNRESOLVED` | yes | **−1** | **+1** | `FAILED_CLOSED_UNRESOLVED` | permanently consumed (fail-closed) |

**Legal transitions** — everything else is rejected, moves no counter, and is audited:

```
                    -> RESERVED
RESERVED            -> EXECUTED | RELEASED | EXPIRED | EXECUTION_UNKNOWN
EXECUTION_UNKNOWN   -> EXECUTED | RELEASED | UNRESOLVED
EXECUTED | RELEASED | EXPIRED | UNRESOLVED  -> (nothing)
```

**Invariants**

```
reserved_count + consumed_count <= cap                       (DB CHECK)
AVAILABLE = cap - reserved_count - consumed_count >= 0
consumption_basis IS NOT NULL  <=>  status IN (EXECUTED, UNRESOLVED)     (DB trigger)
contacts_confirmed = COUNT(EXECUTED) <= contacts_possible
                   = COUNT(EXECUTED) + COUNT(UNRESOLVED)
```
